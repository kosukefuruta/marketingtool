# Owtell SEO診断ツール 有料機能 要件定義書

最終更新: 2026-09-20
対象リリース: 有料版MVPおよび提供開始後の診断統合
関連資料: [プロダクト企画](product-plan.md)、[現行v0.1仕様](seo-audit-v0.1.md)

## 1. 文書の目的

本書は、Owtell SEO診断ツールの有料版について、実装、テスト、運用判断に利用できるレベルでシステム要件を定義する。

有料版の中心価値は、サイトを何度も診断することではなく、SEO上の問題を施策として管理し、実施後の検索実績を継続的に確認できることとする。

## 2. 前提と用語

### 2.1 前提

- 対象はSEO専任者を置きにくい中小企業と個人事業主である
- 初期プランは月額1,980円（税込）前後を想定する
- 有料版MVPは1契約につき1ユーザー、1サイトとする
- 公開中の無料診断は維持するが、有料版MVPの主要機能とは分離する
- 新しい診断項目の追加や診断精度の高度化は、有料版の提供開始後に段階的に行う
- 有料版へ現行診断を統合した後は、サイト全体の定期診断を月1回とする
- 診断統合後はユーザーが任意のタイミングでも診断を開始できる
- 診断統合後の上限は1回300ページとする
- Search Consoleを検索実績データの取得元とする
- 検索結果の直接スクレイピングや有料順位APIは使用しない
- 決済事業者はStripeを第一候補とするが、正式契約前に手数料と運用条件を確認する
- Webアプリケーションと診断ワーカーはKoyeb、PostgreSQLは初期費用を抑えやすいマネージドサービスで運用する想定とする

### 2.2 用語

| 用語 | 定義 |
|---|---|
| サイト | ユーザーが登録した診断対象のWebサイト |
| 診断 | 対象サイトを巡回し、各ページのSEO項目を検査する処理 |
| 診断結果 | ある診断時点で検出された評価、問題、取得値 |
| 施策 | ユーザーが実施状況と効果を管理するSEO改善作業 |
| 実施日 | 施策による変更を公開サイトへ反映した日 |
| 効果測定 | Search Consoleの値を施策実施前後で比較する処理 |
| 基準期間 | 原則として実施日前の28日間 |
| 比較期間 | 原則として実施日後の28日間 |
| 所有確認 | 利用者が対象サイトを管理していることの確認 |

## 3. システムの目標

ユーザーが次の一連の作業を迷わず完了できることを目標とする。

1. アカウントを作成する
2. 自社サイトを登録し、所有を確認する
3. 実施するSEO施策を登録する
4. 施策の進捗と修正内容を記録する
5. 施策を実施済みにし、実施日を登録する
6. 28日、56日、90日後に検索実績の変化を確認する
7. 次に対応する施策を決める

現行診断との統合後は、診断結果から施策を作成する経路も追加する。

## 4. 対象範囲

### 4.1 有料版MVPに含めるもの

- メールOTPによるアカウント登録、ログイン、ログアウト
- メールアドレスの確認
- 有料契約の開始、状態確認、解約
- 1サイトの登録、編集、削除
- Search Consoleを利用したサイト所有確認
- 手動での施策作成
- 施策の一覧、詳細、編集、状態変更、削除
- 修正前、修正後、実施日、メモの記録
- Search Consoleとの接続とデータ同期
- 施策実施前後の検索実績比較
- アプリ内の通知
- 重要な通知と月次サマリーのメール送信

### 4.2 MVPに含めないもの

- 新しい診断項目の追加
- 現行診断項目の判定アルゴリズムの高度化
- 複数ユーザー、招待、組織、細かな権限管理
- 1契約での複数サイト管理
- クライアント向け共有URL
- PDF、CSVなどのレポート出力
- 会計書類の独自発行。決済事業者が提供する領収書等を利用する
- 独自のキーワード順位取得
- 検索ボリューム、被リンク、競合流入の独自データベース
- AIによる記事本文の自動生成
- CMSへの自動修正反映
- ネイティブモバイルアプリ

### 4.3 有料版提供開始後に現行診断と統合するもの

- 初回診断、任意診断、月1回の自動診断
- 診断結果と過去履歴の保存
- 前回診断との差分
- 診断結果からの施策作成

これらはPhase 3で実装する。現行診断を有料版へ接続するものであり、新しい診断項目の追加は含まない。

## 5. 利用者と権限

### 5.1 未ログイン利用者

- 現行の無料診断を利用できる
- 有料版の説明と料金を閲覧できる
- アカウントを作成できる
- 保存済みの診断、施策、Search Consoleデータは閲覧できない

### 5.2 登録済み無料ユーザー

- ログイン、メール確認、契約画面へのアクセスができる
- 有料契約を開始できる
- 有料機能の保存・実行はできない

### 5.3 有料ユーザー

- 本書で定義する有料機能を利用できる
- 自分のサイト、診断結果、施策、検索実績のみ閲覧・変更できる

### 5.4 運営管理者

- ユーザー、契約、サイト、診断ジョブの状態を確認できる
- 失敗した診断や同期を再実行できる
- 問い合わせ調査に必要な範囲で記録を確認できる
- OTPおよびGoogleのアクセストークンを平文で閲覧できない

管理画面の本格実装はMVP後でもよい。MVPでは認証された運営者のみが利用できる最低限の運用コマンドまたは内部画面を用意する。

## 7. 機能要件

要件IDの優先度は、MUSTがその機能を導入するPhaseの必須項目、SHOULDが可能な限り同じPhaseへ含める項目を示す。診断および診断差分の要件はPhase 3に適用し、有料版の初回提供条件には含めない。

### 7.1 アカウントと認証

| ID | 優先度 | 要件 |
|---|---|---|
| AUTH-01 | MUST | メールアドレスへ送信された6桁OTPでアカウントを作成できる |
| AUTH-02 | MUST | OTP確認によってメールアドレスの所有を確認できる |
| AUTH-03 | MUST | メールアドレスとOTPでログインできる |
| AUTH-04 | MUST | ログアウトできる |
| AUTH-05 | MUST | OTPは10分で失効し、試行回数と再送回数を制限できる |
| AUTH-06 | MUST | 未確認メールアドレスでは有料サイトを登録できない |
| AUTH-07 | MUST | セッションを安全なCookieで管理する |
| AUTH-08 | SHOULD | Googleアカウントによるログインを利用できる |
| AUTH-09 | MUST | 退会を申請できる。契約中の場合は解約との関係を明示する |

### 7.2 契約と課金

| ID | 優先度 | 要件 |
|---|---|---|
| BILL-01 | MUST | 月額プランを申し込める |
| BILL-02 | MUST | 決済画面ではカード番号を自システムで保持しない |
| BILL-03 | MUST | 決済事業者のWebhookを検証し、契約状態を反映する |
| BILL-04 | MUST | 契約状態を試用中、有効、支払遅延、解約予約、終了で管理する |
| BILL-05 | MUST | ユーザーが次回更新日前に解約予約できる |
| BILL-06 | MUST | 解約予約後も契約終了日までは有料機能を利用できる |
| BILL-07 | MUST | 支払い失敗後の利用可否と猶予期間を管理できる |
| BILL-08 | MUST | 決済事業者のカスタマーポータルから支払方法等を変更できる |
| BILL-09 | MUST | 同じWebhookを複数回受信しても二重処理しない |
| BILL-10 | SHOULD | 7日または14日の無料試用を設定で有効化できる |

支払い失敗時の猶予期間は7日を仮決めとし、正式な販売条件に合わせて確定する。

### 7.3 サイト登録と所有確認

| ID | 優先度 | 要件 |
|---|---|---|
| SITE-01 | MUST | 有料ユーザーが1サイトを登録できる |
| SITE-02 | MUST | URLを正規化し、HTTPS、ホスト名、末尾スラッシュ等を一貫して扱う |
| SITE-03 | MUST | localhost、プライベートIP、リンクローカルIP、クラウドメタデータ等を対象外にする |
| SITE-04 | MUST | Search Console OAuth接続後、ユーザーが利用可能なプロパティを選択できる |
| SITE-05 | MUST | 選択したSearch Consoleプロパティと登録サイトの対応を確認する |
| SITE-06 | MUST | 所有確認が完了するまで有料診断の保存と定期診断を開始しない |
| SITE-07 | MUST | サイトURL、表示名、タイムゾーンを編集できる |
| SITE-08 | MUST | サイト削除前に影響範囲を表示し、再確認する |
| SITE-09 | SHOULD | Search Consoleが利用できない場合にDNSまたはHTMLによる所有確認を追加できる |

MVPではSearch Console連携を所有確認と効果測定の両方に使用する。Search Consoleを利用していない顧客への対応はMVP後に検討する。

### 7.4 診断

有料版MVPでは現行の診断機能を利用する。以下は新しい診断項目を増やすための要件ではなく、既存診断を有料サービス内で安全に実行・保存するための基盤要件である。

| ID | 優先度 | 要件 |
|---|---|---|
| AUDIT-01 | MUST | サイト登録後に初回診断を開始できる |
| AUDIT-02 | MUST | ユーザーが任意診断を開始できる |
| AUDIT-03 | MUST | 月1回、自動的に定期診断を登録する |
| AUDIT-04 | MUST | 1診断あたり最大300ページを巡回する |
| AUDIT-05 | MUST | 実行待ち、実行中、完了、失敗、取消の状態を保持する |
| AUDIT-06 | MUST | 診断をWebリクエストと別のワーカーで実行する |
| AUDIT-07 | MUST | 診断ジョブと結果を永続化し、アプリ再起動後も失わない |
| AUDIT-08 | MUST | 同一サイトで複数の診断を同時実行しない |
| AUDIT-09 | MUST | 画面を閉じても診断を継続し、再訪時に進捗と結果を確認できる |
| AUDIT-10 | MUST | 診断の開始日時、終了日時、対象URL数、成功数、失敗数を保存する |
| AUDIT-11 | MUST | ページごとの診断項目、評価、取得値、説明を構造化データとして保存する |
| AUDIT-12 | MUST | 結果を良好、要確認、要改善、取得不能の4段階で表示する |
| AUDIT-13 | MUST | 診断失敗時にユーザー向け理由を表示し、安全に再実行できる |
| AUDIT-14 | SHOULD | 診断処理のリトライ回数とバックオフを設定できる |
| AUDIT-15 | SHOULD | robots.txtやサイトマップなどサイト全体の項目も履歴保存する |

任意診断には乱用防止の上限を設ける。MVPの仮値は月4回とし、自動診断1回を含むかどうかは料金確定時に決定する。

### 7.5 診断差分

| ID | 優先度 | 要件 |
|---|---|---|
| DIFF-01 | MUST | 最新診断と直前の正常終了診断を比較できる |
| DIFF-02 | MUST | 新規問題、継続中、解消、評価悪化、評価改善に分類する |
| DIFF-03 | MUST | URLの新規追加と消失を区別する |
| DIFF-04 | MUST | title等の主要な取得値について変更前後を表示する |
| DIFF-05 | SHOULD | 施策に関連する問題が解消した場合、その施策へ候補として表示する |

URL消失は削除、リダイレクト、巡回上限など複数の理由があるため、自動的に問題解消とは判定しない。

### 7.6 施策管理

| ID | 優先度 | 要件 |
|---|---|---|
| ACTION-01 | MUST | 診断結果から施策を作成できる |
| ACTION-02 | MUST | 診断結果と無関係な施策を手動作成できる |
| ACTION-03 | MUST | サイト全体または1つの対象URLを施策へ設定できる |
| ACTION-04 | MUST | 施策名、理由、優先度、状態を保存できる |
| ACTION-05 | MUST | 修正前、修正後、メモをテキストで保存できる |
| ACTION-06 | MUST | 状態を未着手、対応中、実施済み、見送りで管理する |
| ACTION-07 | MUST | 実施済みへ変更する際に実施日を必須とする |
| ACTION-08 | MUST | 実施済みから他の状態へ戻した履歴を保持する |
| ACTION-09 | MUST | 作成日時、更新日時、状態変更日時を保持する |
| ACTION-10 | MUST | 優先度、状態、対象URLで一覧を絞り込める |
| ACTION-11 | MUST | 施策を削除できる。誤操作対策として論理削除する |
| ACTION-12 | SHOULD | 今週取り組む施策として指定できる |
| ACTION-13 | SHOULD | 期限を設定できる |
| ACTION-14 | SHOULD | 同じ診断問題から重複施策を作成しようとした場合に警告する |
| ACTION-15 | SHOULD | 施策の変更履歴を時系列で表示する |

優先度は高、中、低の3段階とする。システムによる推奨優先度とユーザーが設定した優先度は別項目として保持し、ユーザーの設定を上書きしない。

### 7.7 Search Console連携

| ID | 優先度 | 要件 |
|---|---|---|
| GSC-01 | MUST | Google OAuthで必要最小限の権限を取得する |
| GSC-02 | MUST | ユーザーがアクセス可能なSearch Consoleプロパティを一覧表示する |
| GSC-03 | MUST | 選択したプロパティの検索実績を定期取得する |
| GSC-04 | MUST | 日付、ページ、クエリ単位でクリック、表示回数、CTR、平均掲載順位を保存する |
| GSC-05 | MUST | APIの再認証が必要な場合にユーザーへ通知する |
| GSC-06 | MUST | OAuthトークンを暗号化して保存する |
| GSC-07 | MUST | API制限や一時エラー時に安全に再試行する |
| GSC-08 | MUST | 同じ期間の再取得で重複データを作らない |
| GSC-09 | MUST | 連携を解除し、保存トークンを無効化または削除できる |
| GSC-10 | SHOULD | データ最終同期日時と取得対象期間を表示する |

データは毎日1回同期する。Search Consoleの値は後から更新される可能性があるため、直近7日分を毎回再取得する。取得期間と再取得幅は運用実績に応じて変更可能にする。

### 7.8 効果測定

| ID | 優先度 | 要件 |
|---|---|---|
| EFFECT-01 | MUST | 実施日を基準に、実施前28日間の基準値を計算する |
| EFFECT-02 | MUST | 実施後28日間のデータが揃った時点で最初の比較結果を表示する |
| EFFECT-03 | MUST | 実施56日後、90日後にも経過を確認できる |
| EFFECT-04 | MUST | 表示回数、クリック数、CTR、平均掲載順位を比較する |
| EFFECT-05 | MUST | 対象URLがある施策はそのURLのデータを使用する |
| EFFECT-06 | MUST | サイト全体の施策はプロパティ全体のデータを使用する |
| EFFECT-07 | MUST | データ不足、表示回数が少ない、連携切れを判定不能として表示する |
| EFFECT-08 | MUST | 変化率と実数の両方を表示する |
| EFFECT-09 | MUST | 結果を施策の因果効果と断定せず、実施後に観測された変化と表示する |
| EFFECT-10 | MUST | ユーザーが改善、変化なし、悪化、判定保留を手動記録できる |
| EFFECT-11 | SHOULD | システムの参考判定を表示する |
| EFFECT-12 | SHOULD | 比較対象クエリをユーザーが指定できる |

実施日当日は変更反映途中の可能性があるため、初期仕様では前後両期間から除外する。複数施策が同じページで期間重複している場合は、その事実を表示して単独施策の効果と誤認させない。

### 7.9 ダッシュボード

| ID | 優先度 | 要件 |
|---|---|---|
| DASH-01 | MUST | 優先度が高い未着手施策を表示する |
| DASH-02 | MUST | 対応中の施策を表示する |
| DASH-03 | MUST | 効果測定待ちの施策と測定可能になる日を表示する |
| DASH-04 | MUST | 測定可能になった施策を表示する |
| DASH-05 | MUST | 最新診断の概要と前回との差分を表示する |
| DASH-06 | MUST | Search Consoleの直近28日と前28日の主要指標を表示する |
| DASH-07 | SHOULD | 今週取り組む施策を最大3件表示する |
| DASH-08 | SHOULD | 改善した施策と悪化した施策を表示する |

画面の主役は診断スコアではなく、次に行う施策と測定待ちの施策とする。

### 7.10 通知

| ID | 優先度 | 要件 |
|---|---|---|
| NOTIFY-01 | MUST | アプリ内通知を表示する |
| NOTIFY-02 | MUST | 診断完了または失敗を通知する |
| NOTIFY-03 | MUST | 効果測定可能日を迎えた施策を通知する |
| NOTIFY-04 | MUST | Search Consoleの再認証が必要な場合に通知する |
| NOTIFY-05 | MUST | 支払い失敗と契約終了予定を通知する |
| NOTIFY-06 | SHOULD | 月次サマリーをメール送信する |
| NOTIFY-07 | SHOULD | ユーザーが任意通知を停止できる |

契約、セキュリティ、連携切れに関する重要通知は、任意通知を停止していても送信できるものとする。

## 8. 主要な業務ルール

### 8.1 施策の状態遷移

```text
未着手 → 対応中 → 実施済み
   └──────→ 見送り

対応中 → 未着手 / 見送り
実施済み → 対応中
見送り → 未着手
```

- 実施済みへの変更には実施日が必要
- 実施日を変更した場合は効果測定期間を再計算する
- 実施済みを解除しても過去の状態履歴と測定結果を消さない
- 見送り理由は任意入力とする

### 8.2 診断スケジュール

- 初回診断はサイト登録完了後にユーザーが開始する
- 定期診断日は初回診断の完了日を基準とする
- 前回診断が実行中の場合は新しい定期診断を重複登録しない
- 失敗時は最大2回自動再試行し、最終失敗をユーザーへ通知する
- 定期診断予定日に契約が無効な場合は実行しない

### 8.3 契約終了後

- 新しい診断、同期、施策の作成・更新を停止する
- 終了後30日間はユーザーが保存済みデータを閲覧できる
- 30日後にユーザー画面からアクセスできない状態にする
- 法令や会計上必要な契約記録を除き、終了後90日以内にサイト診断・施策・検索実績データを削除する
- 再契約時の復元可否は、削除前である場合に限る

保存期間は利用規約とプライバシーポリシーに明示する。

## 9. データ要件

### 9.1 主要エンティティ

| エンティティ | 主な内容 |
|---|---|
| users | メールアドレス、確認状態、タイムゾーン |
| sessions | ログインセッション、有効期限、失効状態 |
| subscriptions | プラン、契約状態、決済事業者ID、更新日、終了日 |
| sites | 所有者、URL、表示名、Search Consoleプロパティ、所有確認状態 |
| oauth_connections | Google接続、暗号化トークン、権限、有効期限、接続状態 |
| audit_jobs | 診断種別、状態、進捗、開始・終了日時、失敗理由 |
| audit_pages | 診断時のURL、HTTP状態、取得状態、主要SEO値 |
| audit_checks | ページまたはサイト単位の診断項目、評価、詳細、構造化値 |
| actions | 施策名、対象URL、理由、優先度、状態、修正前後、実施日 |
| action_sources | 施策と診断項目の関連 |
| action_events | 状態変更や内容変更の履歴 |
| search_performance | 日付、ページ、クエリ、クリック、表示、CTR、平均掲載順位 |
| effect_measurements | 施策、測定時点、比較期間、各指標、参考判定、手動判定 |
| notifications | 種別、本文、既読状態、送信状態 |
| webhook_events | 外部イベントID、処理状態、受信日時 |

### 9.2 データ制約

- すべての業務データにユーザーまたはサイトの所有関係を持たせる
- 日時はデータベースではUTCで保存し、表示時にユーザーのタイムゾーンへ変換する
- 金額は最小通貨単位の整数で保存する
- URLは表示用の原文と比較用の正規化値を必要に応じて分ける
- 診断結果はMarkdownだけでなく構造化して保存する
- 検索実績は同一サイト、日付、ページ、クエリ等の組み合わせで重複しないようにする
- 監査上必要な契約イベントと施策状態変更は物理削除しない

## 10. システム構成要件

### 10.1 構成

```text
ブラウザ
  ↓
Webアプリ / API
  ├─ PostgreSQL
  ├─ ジョブキュー
  ├─ 診断ワーカー
  ├─ Search Console同期ワーカー
  ├─ メール配信サービス
  ├─ Google OAuth / Search Console API
  └─ 決済サービス
```

### 10.2 方針

- 現行のメモリ内ジョブ管理を有料版へ流用しない
- Webプロセスの再起動で診断状態や結果が失われない構成にする
- 診断はWebプロセスから直接長時間実行せず、永続キューを介してワーカーが処理する
- PostgreSQLを正本データストアとする
- 診断ワーカーをWebアプリと独立して増減または再起動できるようにする
- 定期診断、Search Console同期、通知はスケジューラーからジョブ登録する
- 同一ジョブの重複実行を防ぐ冪等性キーを持つ
- 将来的に複数インスタンスへ拡張できる構成にする

診断レポート全文や大きな成果物をDBへ保存するかオブジェクトストレージへ保存するかは、実データ量を測定して詳細設計で決定する。ページ・診断項目・施策との関連に必要な構造化データはDBへ保存する。

## 11. 非機能要件

### 11.1 性能

- 通常の画面およびAPIは、外部API待ちを除き95パーセンタイル2秒以内を目標とする
- 診断開始要求はジョブ登録後3秒以内に応答する
- 300ページ診断は10分以内の完了を目標とするが、対象サイトの応答速度に依存する旨を表示する
- 診断中も他ユーザーの画面操作を阻害しない

### 11.2 可用性と復旧

- 月間稼働率99.5%以上を初期目標とする。ただし外部サービス障害を除く
- アプリ再起動後、実行中だったジョブを失敗確定または安全に再開できる
- PostgreSQLの自動バックアップを毎日取得する
- 目標復旧時点は24時間以内、目標復旧時間は8時間以内とする
- バックアップからの復旧手順を文書化し、定期的に確認する

### 11.3 セキュリティ

- 通信はHTTPSのみとする
- OTPは暗号化して保存し、期限切れまたは使用済みの値を再利用できないようにする
- セッションCookieにSecure、HttpOnly、SameSite属性を設定する
- 状態変更リクエストをCSRFから保護する
- 入力値を検証し、出力時に適切にエスケープする
- 診断機能にSSRF対策を実装し、DNS再解決後の接続先も検査する
- Google OAuthトークンはアプリケーションレベルで暗号化する
- シークレットをリポジトリやログへ出力しない
- 決済Webhookの署名を検証する
- ログイン、診断開始、OAuth接続、契約変更にレート制限を設ける
- ユーザー間のデータ分離をAPIとDBアクセスの両方で検証する
- 管理操作を監査ログへ記録する

### 11.4 プライバシー

- Googleから取得するデータ、利用目的、保存期間、削除方法を明示する
- 必要最小限のOAuthスコープだけを要求する
- 退会および連携解除時のデータ削除手続きを用意する
- アプリログへ検索クエリを不要に出力しない
- 個人情報を含む可能性のある自由記述欄を保護対象として扱う

### 11.5 アクセシビリティと対応環境

- キーボードのみで主要操作を完了できる
- 状態を色だけで表現しない
- フォームのラベル、エラー、フォーカス状態を明確にする
- 最新2世代のChrome、Safari、Edge、Firefoxを対象とする
- スマートフォン幅でも施策の確認と状態変更ができる

### 11.6 運用監視

- Web、診断、同期、通知ごとに構造化ログを記録する
- リクエストIDとジョブIDで処理を追跡できる
- エラー率、キュー滞留数、診断時間、同期失敗数、Webhook失敗数を監視する
- 診断ジョブの長時間停止、定期処理未実行、DB接続失敗を運営者へ通知する
- ユーザー向けエラーには内部情報やスタックトレースを表示しない

## 12. 代表的な受け入れ条件

### 12.1 初回利用

- 新規ユーザーがメール確認、契約、Google接続、サイト選択、初回診断開始まで完了できる
- 画面を閉じ、別端末から再ログインしても診断状況を確認できる
- 診断完了後、ページ別の評価が表示され、要改善項目から施策を作成できる

### 12.2 施策管理

- 作成した施策を未着手から対応中へ変更できる
- 実施日なしでは実施済みにできず、入力理由が表示される
- 実施済みにすると28日後、56日後、90日後の測定予定日が表示される
- 状態を戻しても変更履歴が残る

### 12.3 効果測定

- 対象URLの実施前後データが揃うと4指標の実数と変化率が表示される
- データが不足する場合は0として扱わず、判定不能の理由が表示される
- 同じページで複数施策が重なる場合は注意が表示される
- ユーザーが最終的な効果判定とメモを保存できる

### 12.4 障害と再実行

- Webプロセス再起動後も診断ジョブと完了済み結果が失われない
- Search Console APIの一時エラーでは自動再試行される
- 再認証が必要な場合は同期を失敗し続けず、ユーザーへ再接続を案内する
- 同じ決済Webhookを再送しても契約や通知が二重作成されない

## 13. リリース段階

### Phase 1: 有料サービス基盤と施策管理

- 認証
- 1サイト登録
- 月額課金と契約管理
- 手動による施策の作成、編集、状態管理
- 修正前後、実施日、メモ、変更履歴
- ダッシュボードの基本表示

この段階では少人数の招待ユーザーによる検証を行う。診断項目の追加は行わない。

### Phase 2: Search Consoleと正式な有料提供

- Google OAuth
- 所有確認
- 検索実績の同期
- 28日、56日、90日の効果測定
- アプリ内通知
- メール通知
- 月次サマリー
- 法務表示とデータ削除運用
- 運用監視と復旧手順

ここまでで、診断機能に依存せず、ユーザーが任意のSEO施策を登録し、実行と効果を管理できる有料版を正式提供する。対象ユーザーに実際の施策を登録してもらい、利用頻度と理解しやすさを検証する。

### Phase 3: 現行診断との統合

- 現行診断結果の永続保存
- 診断結果からの施策作成
- 診断履歴と前回との差分
- 永続診断ジョブ
- 月1回の定期診断

この段階でも診断項目と判定ロジックは現行仕様を維持し、有料版の施策管理へ接続することに集中する。

### Phase 4: 診断機能の段階的な拡張

- 利用者が施策として多く登録する課題を集計する
- 要望、改善効果、実装・運用コストから追加項目を選ぶ
- 1項目または小さなまとまりごとに追加する
- 追加前後で施策作成率と実施率を確認する

候補には、構造化データ、Core Web Vitals、内部リンク、重複コンテンツなどがあるが、利用実績に基づいて優先順位を決める。

## 14. リリース判断指標

有料版の正式提供前に、少なくとも次を確認する。

- 初期設定後に施策を1件以上作成したユーザーの割合
- 作成した施策を実施済みにした割合
- 28日後に効果測定画面へ戻ったユーザーの割合
- Search Console接続成功率と同期成功率
- ユーザーが「次に何をすべきか」を理解できた割合
- 月額1,980円に対する支払い意向

診断統合前には、加えて1ユーザーあたりの診断時間、インフラ費用、診断結果からの施策作成率を確認する。

継続利用の価値が確認できるまでは、巡回ページ数や診断項目を大幅に増やすことを優先しない。

有料版の正式提供に必要なのは、施策を記録し、実施し、効果を確認できることである。新しい診断項目の追加は正式提供のリリース条件にしない。

## 15. 詳細設計前に確定する事項

以下は要件の方向性を変えずに、実装着手前または各Phase開始前に確定する。

1. 正式な価格、税込表示、無料試用の有無
2. 任意診断の月間回数上限
3. 支払い失敗時の猶予期間
4. 契約終了後の閲覧期間と削除期間
5. 利用する認証、メール、決済サービス
6. Koyeb上のWeb・ワーカー・スケジューラーと、マネージドPostgreSQLの構成
7. Google OAuth審査と必要なプライバシー文書
8. 効果の参考判定に用いる最低表示回数と閾値
9. 月次サマリーの内容と送信日

これらは環境変数または管理設定として変更できるようにし、コード内へ固定しないことを原則とする。
