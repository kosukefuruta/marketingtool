# 施策型カタログ（案）

最終更新: 2026-09-27
関連資料: [目標駆動型SEO施策エンジン構想](goal-driven-action-planning.md)、[プロダクト企画](product-plan.md)、[DataForSEO調査](dataforseo-research.md)

## 1. この文書の位置づけ

ブレークダウンの各ドライバーに「必要値」と「差分」を表示できるようになった。次は差分を施策へ変換する。そのために、Owtellが扱う施策型を有限個で定義する。

構想文書§17.1の手順4・5にあたる。施策型が決まらないと、どのデータをいつ取得すべきかも決まらないため、データ取得の実装より先にこの定義を置く。

## 2. 2層に分ける

| 層 | 置き場所 | 内容 |
|---|---|---|
| 施策型 | コード（固定） | サイトに依存しない条件と操作。本文書が定義する |
| 施策インスタンス | 実行時に生成 | 利用者のデータを条件に当てて生成する具体的な施策。対象URLなどはクロール結果から決まる |

利用者に見えるのは具体、コードにあるのは汎用とする。

## 3. 網羅性の検査方法

構想文書§14に従い、次の3方向で検査する。

1. **目標から下向き**: 目標 → KPI → 変化要因 → 状態 → 施策。施策へ到達できない変化要因があれば不足
2. **データから上向き**: データ → 状態 → ギャップ → 施策 → 目標。どこにも繋がらないデータは優先度が低い
3. **作用点による横断**: §14.5の12作用点をすべて通す

初版（ドライバー別の分類）では、順位・外部評価・表示速度UX・維持監視の4作用点が空だった。本版は作用点を第一の軸にする。

## 4. データの可用性

| 記号 | 意味 |
|---|---|
| ○ | 現在取得している |
| △ | 取得手段はあるが未実装 |
| × | 取得手段そのものが未定 |

現在取得しているもの。

- **診断（最大300ページ）**: HTTPステータス、最終URL、title、meta description、H1個数、canonical、lang、noindex、本文文字数、画像alt、robots.txt、XMLサイトマップ、サイトマップ巡回、発見URL数、title・descriptionの重複
- **Search Console**: サイト全体の表示回数・クリック数・CTR、登録キーワードの平均掲載順位
- **GA4**: セッション、PV、セッションあたりPV、広告収益、自然検索セッション、CTAパス別セッション、キーイベント別セッション

| 作用点 | 状態判定 | 対応施策 | 効果予測 | 効果測定 |

| 発見・クロール | ○（内部リンク除く） | ○ | △ | ○ |

| 検索意図・関連性 | △（クエリ次元が必要） | ○ | × | △ |
| 検索結果での訴求 | △（ページ次元が必要） | ○ | ×（期待CTR表が無い） | △ |

`×` と `△` が仕様上の欠落である。施策型は12作用点すべてに存在するが、**状態を判定できるのは発見・クロール、インデックス、回遊、コンバージョンの4作用点だけ**である。

## 9. 初期実装スコープ

追加データなしで候補を生成できるのは次の8施策型のみ。

## 10. 決めていないこと

| 項目 | 内容 |
|---|---|
| 閾値 | 「表示回数が閾値以上」「本文が基準未満」の具体値。サイトジャンル別に変える必要があるか |
| 効果の見積り | 各施策型がドライバーをどれだけ動かすか |
| 成功確率 | 施策型ごとの成功率 |
| 優先順位 | 差分の大きさ、工数、成功確率の合成方法 |
| 複数シグナルの合成 | 構想§8.3のとおり単一シグナルで断定しない。CTR低下の原因が順位なのか意図不一致なのかを切り分ける証拠 |
| 施策インスタンスの保存 | 候補をいつDBへ保存するか。構想§11は候補と実行を分ける |
| 実行者の条件 | 記事作成のような工数の大きい施策を、利用者の使える時間に応じてどう出し分けるか |
