# Owtell 目標駆動型SEO施策エンジン構想

作成日: 2026-09-21  
状態: 企画・設計検討中  
関連資料: [プロダクト企画](product-plan.md)、[競合機能調査](competitive-feature-analysis.md)、[有料機能要件定義](paid-feature-requirements.md)

## 1. 文書の目的

本書は、Owtellを単発のSEO診断ツールから、目標達成に必要な施策を計画・実行・評価するシステムへ発展させるための議論を記録する。

特に、次の論点を整理する。

- 取得するデータの目的
- 現在状態と目標の関係
- 施策型と施策インスタンス
- データと目標から施策候補を生成する方法
- 施策の効果予測
- ユーザー別の難易度と優先順位
- 目標達成までのフェーズと施策の順序
- 施策体系の抜け漏れを減らす方法
- 実施結果を次の計画へ還元する循環

本書に記載する数値例は概念を説明するための例であり、製品上の予測係数として確定したものではない。

## 2. 中心となるプロダクト定義

Owtellがデータを取得する目的は、分析画面やグラフを増やすことではなく、利用者の目標達成に必要な施策を導き出すことである。

> Owtellは、既存データと目標から施策候補を生成し、利用者ごとの実現可能性、期待効果、費用対効果を評価して実行順序を提案し、その結果を次の計画へ還元するSEO改善管理システムである。

基本的な循環は次の通りである。

```text
既存データ・目標・利用者の実行条件
                ↓
現在状態と目標状態の差を特定
                ↓
施策候補を生成
                ↓
予測効果・難易度・費用対効果を評価
                ↓
施策セットと実行順序を決定
                ↓
実行・記録・効果測定
                ↓
新しい事実・時系列・実行実績として次の計画へ還元
```

## 3. データソースと洞察を分離する

当初は「問題発見」「機会発見」「施策管理・効果測定」を3本柱とする案があった。しかし、問題と機会はデータソースに対応しない。

- サイトデータから、リンク切れのような問題も、内容追加のような成長機会も見つかる
- Search Consoleから、高表示・低CTRの機会も、クリック急減の問題も見つかる
- GA4から、CV低下の問題も、高CVページの横展開機会も見つかる

したがって、内部データは少なくとも次の2軸を分けて持つ。

### 3.1 データソース

- サイトクロール・ページ内容
- Google Search Console
- Google Analytics 4
- ユーザーによる目標・入力情報
- 施策の実行履歴
- 将来の競合データ
- 将来のAI検索データ
- 将来の外部キーワード・被リンクデータ

### 3.2 洞察の種類

- 問題・リスク
- 成長機会
- 重要な変化
- 観測事項
- データ不足・要調査

データはソース別に取得するが、ユーザーへ提示する改善候補は複数ソースを統合する。

```text
titleに問題がある
＋ 表示回数が多い
＋ CTRが期待値より低い
＋ 目標キーワードと関係が深い
＝ 優先して検討すべきtitle改善施策
```

## 4. インプットデータ

### 4.1 既存データ

既存データは、現在の事実と時系列に分ける。

#### 現在の事実

- URL、ページ種別、サイト階層
- title、description、見出し、本文、画像
- canonical、robots、noindex、sitemap
- HTTP状態、リダイレクト、内部・外部リンク
- インデックス状態
- 対象クエリ、表示回数、クリック、CTR、平均掲載順位
- セッション、行動イベント、コンバージョン
- 売上高、平均CV単価
- PV、広告収益、1,000PVあたり広告収益（Page RPM）
- 現在の目標ページ、対象キーワード

#### 時系列

- 診断結果の変化
- ページ内容の変化
- 順位、表示回数、CTR、クリックの推移
- セッション、CVR、コンバージョンの推移
- 施策の作成、採用、実施、見送りの履歴
- 実施後に観測された効果
- 予測値と実測値の差

時系列により、「現在悪い」だけでなく、悪化中、改善中、停滞中、施策後に変化した、といった判断を行う。

### 4.2 目標

目標は大・中・小の階層で管理する。

| 階層 | 例 |
|---|---|
| 大目標 | Webサイト経由の問い合わせを月20件にする |
| 中目標 | 自然検索経由の問い合わせを月10件にする |
| 小目標 | 「東京 Web制作」で10位以内に入る |
| 指標 | 順位、表示回数、CTR、クリック、CV数 |
| 期限 | 2027年3月まで |

目標には次を持たせる。

- 目標の種類
- 対象サイト、ページ、キーワード、クラスター
- 現在値
- 目標値
- 期限
- 上位目標と下位目標
- 成功判定指標
- 事業上の価値
- 状態

目標、指標、施策を混同しない。

- 目標: 達成したい結果
- 指標: 達成状況を測る数値
- 施策: 目標へ近づくために実行する作業

売上高と広告収益は異なる効果経路として管理する。

```text
売上高 = CV数 × 平均CV単価
広告収益 = PV ÷ 1,000 × 広告RPM
```

売上目標では平均CV単価から必要CV数を逆算し、広告収益目標では広告RPMから必要PVを逆算する。GA4等から取得できる場合は実測値を使用し、取得できない場合はユーザーが入力した仮定値を使用する。仮定値と実測値は出所を区別する。

### 4.3 利用者の実行条件

同じ施策でも、利用者によって難易度、費用、完了期間が異なる。初期値として次を確認する案がある。

- 使用CMS・サイト構成
- 自分でページを編集できるか
- 開発担当者や制作会社がいるか
- SEOに使える時間
- 月間予算
- 新規記事を作成できる頻度
- 承認・公開に必要な期間

利用開始後は実績で補正する。

- 同種施策の実際の完了日数
- 採用・見送り傾向
- 外部依頼の必要性
- 実施された施策の難易度評価
- 施策型ごとの成果

## 5. 目標起点とデータ起点

施策候補には2つの入口がある。

### 5.1 目標起点の計画

目標から逆算し、理想状態へ到達するために必要な変化を列挙する。

```text
自然検索CVを月10件増やす
├─ クリック数を増やす
│  ├─ 表示回数を増やす
│  └─ CTRを上げる
└─ CVRを上げる
```

これは「何が達成できれば目標へ届くか」を示し、施策の探索空間を作る。目標だけでは、どのページのどの施策が最適かまでは確定しない。

### 5.2 データ起点の評価

現在データから、伸び代、実現可能性、必要コスト、効果発現期間を評価する。

例えば、同じキーワードでも現在状態により方針が異なる。

| 現在状態 | 主な判断 |
|---|---|
| 1位・CTRも高い | 順位・CTRの伸び代は小さい。維持、CVR、関連語を検討する |
| 1位・CTRが低い | スニペットや検索意図を確認する |
| 5位前後 | 内容、内部リンク、CTRの複合改善を検討する |
| 10位前後 | 比較的小さな改善で大きな増分が得られる可能性がある |
| 30位前後 | 検索意図、ページの役割、内容を再検討する |
| 100位前後 | 伸び代は大きいが成功確率と必要期間を慎重に評価する |
| 圏外・ページあり | インデックス、意図不一致、品質、対象ページを確認する |
| 圏外・ページなし | 新規ページ作成の投資判断を行う |

### 5.3 両者の統合

目標起点とデータ起点は対立しない。

- 目標は、行く方向と施策の価値を決める
- データは、現在位置、伸び代、通りやすい経路を決める

```text
目標から必要な変化と施策型を列挙
        ＋
データから伸び代・難易度・成功確率を評価
        ↓
目標へ効率よく近づく施策を選択
```

## 6. 因果構造と状態モデル

施策だけから出発すると「思いついた施策集」になり、データだけから出発すると「取得できるデータに引っ張られた分析ツール」になる。そのため、中心には目標に至る因果構造を置く。

```text
目標
↓
目標を構成するKPI
↓
KPIを変化させる要因
↓
要因の現在状態
↓
状態を変える施策
↓
状態を観測するデータ
```

### 6.1 例: 自然検索CV

```text
自然検索CV
├─ クリック数
│  ├─ 表示回数
│  │  ├─ 検索需要
│  │  ├─ インデックス
│  │  ├─ 対象クエリ数
│  │  └─ 掲載順位
│  └─ CTR
│     ├─ 掲載順位
│     ├─ title
│     ├─ description
│     ├─ 検索意図との一致
│     └─ 検索結果での見え方
└─ CVR
   ├─ ページとニーズの一致
   ├─ 商品・サービスの訴求
   ├─ CTA
   ├─ 導線
   ├─ 信頼性
   └─ フォーム
```

この構造は因果関係の仮説である。相関しか確認できない関係を断定せず、根拠と確信度を保持する。

### 6.2 状態を中間層に置く

データから施策を直接決定せず、状態を推定してから目標との差を評価する。

```text
データ
↓ 観測・推定
現在状態
↓ 目標状態と比較
ギャップ
↓ 状態を変える操作
施策インスタンス
```

例えば「平均順位12位」だけではリライトを確定しない。

- 内容に不足があるなら、リライト
- 内容が十分で内部リンクが弱いなら、内部リンク追加
- 検索意図が異なるなら、ページの再設計
- 複数ページが競合するなら、統合または役割整理
- 順位が上昇中なら、追加変更せず観測
- 変更直後なら、効果測定まで待機

## 7. 施策型と施策インスタンス

施策は「何を」「どうする」に分解する。

```text
施策型 = 対象（何を）× 操作（どうする）
施策インスタンス = 施策型 ＋ 対象URL・キーワード・具体的内容
```

個別ページやキーワードの組み合わせは多数存在するが、施策型は有限のカタログとして管理できる。

### 7.1 対象の例

- title、meta description
- H1・見出し、本文
- 画像・alt
- 構造化データ
- canonical、robots、noindex、sitemap
- URL、リダイレクト
- 内部リンク、外部リンク
- 表示速度、モバイル表示
- CTA、フォーム
- 個別ページ、ページ群、テンプレート、サイト構造
- 対策キーワード、検索意図、キーワードクラスター

### 7.2 操作の例

- 作成する
- 追加する
- 削除する
- 修正する
- 書き換える
- 統合する
- 分割する
- 移動する
- 接続する
- 転送する
- 設定する
- 解除する
- 高速化する
- 観測する
- 維持する

### 7.3 施策型の例

| 施策型ID | 対象 | 操作 |
|---|---|---|
| `TITLE_REWRITE` | title | 書き換える |
| `DESCRIPTION_REWRITE` | meta description | 書き換える |
| `CONTENT_ADD_TOPIC` | 本文 | 不足トピックを追加する |
| `PAGE_CREATE` | ページ | 作成する |
| `PAGE_MERGE` | 複数ページ | 統合する |
| `INTERNAL_LINK_ADD` | 内部リンク | 追加する |
| `BROKEN_LINK_FIX` | リンク切れ | 修正する |
| `REDIRECT_CREATE` | URL | 転送する |
| `NOINDEX_REMOVE` | noindex | 解除する |
| `CANONICAL_SET` | canonical | 設定する |
| `STRUCTURED_DATA_ADD` | 構造化データ | 追加する |
| `IMAGE_OPTIMIZE` | 画像 | 軽量化する |
| `CTA_REWRITE` | CTA | 書き換える |
| `FORM_SIMPLIFY` | フォーム | 簡略化する |

### 7.4 原子施策と複合施策

効果の学習には、施策を小さな原子施策へ分ける必要がある。

```text
ページをリライトする
├─ titleを書き換える
├─ 見出しを追加する
├─ 不足トピックを追加する
├─ 古い情報を更新する
└─ 関連ページから内部リンクを追加する
```

内部では原子施策を記録し、画面では利用者が扱いやすい複合施策や施策パッケージとしてまとめる。

### 7.5 施策型の定義情報

施策型には次を持たせる。

- ID、名称、対象、操作
- 適用可能な目標
- 適用条件、除外条件
- 必要なデータとシグナル
- 変化させる状態・指標
- 直接効果、関連効果、サイト全体への効果
- 標準難易度、標準作業時間、標準費用
- 効果発現期間
- 依存する施策、競合する施策
- 効果予測モデル
- 効果測定指標と測定時期
- 根拠、確信度、ルールバージョン

### 7.6 施策インスタンスの情報

- 施策型ID
- 対象サイト、URL、ページ群、キーワード
- 関連する目標とフェーズ
- 生成理由と根拠データ
- 現在値と提案値
- この利用者における難易度、時間、費用
- 保守・基準・楽観の予測
- 優先順位と選定理由
- 候補、採用、対応中、実施済み等の状態
- 実施日、修正前、修正後、メモ
- 実測結果と予測との差

### 7.7 実装方式の案

Javaのクラスとインスタンスに相当する考え方だが、施策ごとにコード上のクラスを大量作成するとは限らない。

1. 施策型の定義をDBまたは設定として管理する
2. CTR改善型、順位改善型、インデックス改善型、CVR改善型などの共通判定・予測処理をコードで持つ
3. 特定ページ・キーワードへ適用した施策インスタンスをDBへ保存する

## 8. 施策候補の生成

### 8.1 生データを共通シグナルへ変換する

判定ルールが各データソースの生データを直接参照し続けると、条件が重複して保守しにくい。再利用可能なシグナルへ正規化する。

例:

```text
high_impressions
ctr_below_expected
ranking_4_to_10
ranking_11_to_20
ranking_declining
clicks_declining
query_page_mismatch
multiple_pages_for_same_query
thin_content
missing_title
weak_internal_links
not_indexed
slow_page
high_organic_exit_rate
goal_keyword
goal_page
recently_changed
insufficient_data
```

`ctr_below_expected`は固定値だけで判定しない。順位、端末、ブランド・非ブランド、検索での見え方、データ量等を考慮した期待CTRとの差として扱う。

### 8.2 生成処理

```text
1. 目標から関連する因果構造と施策型を絞る
2. データから現在状態を推定する
3. 目標状態とのギャップを列挙する
4. ギャップを解消できる施策型を検索する
5. 適用条件と除外条件を評価する
6. 対象ページ等を設定して施策インスタンスを生成する
7. 効果、成功確率、難易度、期間、費用を予測する
8. 重複、競合、依存関係を整理する
9. 利用者別に優先順位を付ける
```

目標だけから全URL分の施策インスタンスを先に保存するのではなく、目標から施策の探索範囲を作り、データに適合するものだけを具体化する。

### 8.3 単一シグナルで施策を断定しない

「高表示・低CTRなら必ずtitle変更」「10位前後なら必ずリライト」といった単純ルールは避ける。

高表示・低CTRには次の可能性がある。

- 順位が低いためCTRが低い
- ブランド検索等の検索意図とページが一致しない
- 広告や検索機能によりクリックされにくい
- titleがページ内容と一致しない
- Googleがtitleを書き換えている
- 十分な観測量がない

複数の状態と証拠を組み合わせ、候補、代替案、確信度を出す。

### 8.4 重複と粒度の整理

同じページに次の候補が出る可能性がある。

- titleを改善する
- CTRを改善する
- 検索意図に合わせる
- 目標キーワードをtitleへ反映する

これらは「検索結果での訴求を改善する」という複合施策へまとめ、内部に原子施策と各ルールの根拠を持たせる。

同じ原因がテンプレートや多数ページへ及ぶ場合は、URLごとの施策ではなくページ群・テンプレート単位の施策へ統合する。

## 9. 施策の効果予測

施策には、何をするかだけでなく、目標に対してどのような変化を予想するかを持たせる。

> 施策 = 実行内容 + 変化の予測 + 根拠 + 測定方法

### 9.1 効果経路

例として、順位を10位前後から5位前後へ上げる場合を考える。

```text
リライト・内部リンク追加
        ↓
検索意図への適合性やページ評価が改善
        ↓
平均掲載順位 10位 → 5位
        ↓
表示回数が増加
        ↓
順位上昇とスニペット改善によりCTRが増加
        ↓
クリックが増加
        ↓
CVRを維持できればCVが増加
        ↓
関連ページや関連クエリへ波及する可能性
```

例として、表示回数が2倍、CTRが相対的に20%増加すると仮定する。

```text
現在:
10,000表示 × CTR 2.0% = 200クリック

施策後:
20,000表示 × CTR 2.4% = 480クリック

クリック倍率:
480 ÷ 200 = 2.4倍
```

現在のCVRが3%で維持される場合は、6CVから14.4CVとなり、期待増分は約8CVとなる。この数値は説明用であり、実際にはサイト固有のデータから係数を求める。

### 9.2 予測の種類

- 直接効果: 対象ページの順位、表示回数、CTR、クリック、CV
- 関連効果: 関連クエリ、ロングテール、内部リンク先、同一クラスター
- サイト全体への効果: クロール効率、テーマ評価、ブランド・信頼性等

数値化できない効果も捨てず、方向、対象範囲、確信度を保存する。

### 9.3 シナリオと不確実性

一点予測ではなく、保守・基準・楽観のシナリオを持つ。

| シナリオ | 例: 到達順位 | 例: クリック | 例: CV |
|---|---:|---:|---:|
| 保守的 | 8位 | 280 | 8 |
| 基準 | 5位 | 480 | 14 |
| 楽観的 | 3位 | 720 | 22 |

予測には次を表示する。

- 予測期間
- 予測範囲
- 確信度
- 前提条件
- 根拠データ
- 数値化できない副次効果

SEOの変化は競合、検索需要、Googleの更新、同時期の他施策等に影響されるため、因果関係を断定しない。

### 9.4 MVPの予測式

初期版は説明可能な簡易モデルでよい。

```text
予測表示回数
= 現在の表示回数 × 順位変化等による露出係数

予測CTR
= 現在のCTR × 順位変化係数 × スニペット改善係数

予測クリック
= 予測表示回数 × 予測CTR

予測CV
= 予測クリック × 予測CVR
```

順位による表示回数・CTRへの影響を二重計上しないよう、係数の役割を明確にする。

### 9.5 予測値の改善

1. 一般的な初期係数を仮置きする
2. サイト自身のGSCから順位別・端末別・クエリ種別の実績を求める
3. GA4からページ・流入別CVRを求める
4. 過去施策から成功率、変化量、効果発現期間を集計する
5. サイト固有・施策型固有の係数へ補正する

一般統計より、そのサイト自身の実績を優先する。

## 10. 伸び代、成功確率、費用対効果

### 10.1 伸び代

```text
伸び代
= 目標状態または到達可能状態で期待される成果
- 現在の成果
```

### 10.2 成功確率

次の要素から推定する。

- 現在順位と目標順位の差
- 上昇・下降・停滞の傾向
- 検索意図との一致
- 内容・内部リンク・技術上の不足
- 上位競合との差
- サイトの同分野での過去実績
- 実施できる施策の種類
- 効果発現期間
- データ量と予測根拠

### 10.3 期待成果

```text
期待成果増分
= 最大または基準となる伸び代 × 成功確率
```

例えば、100位から5位への理論上の増分が大きくても成功確率が低ければ、10位から5位へ上げる施策の方が期待値で上回る可能性がある。

### 10.4 優先順位

概念上は次の要素を使う。

```text
優先度
= 目標への期待貢献
× 予測確信度
× 波及範囲
÷ 実行負荷
÷ 必要費用
÷ 効果発現期間
```

ただし、単一の不透明な点数だけを表示しない。期待CV、成功確率、作業時間、費用、期間、確信度、推奨理由を分けて利用者へ説明する。

## 11. 施策候補と実行施策を分ける

候補をすべてタスク一覧へ入れると、利用者に圧迫感を与える。候補と、実行を決めた施策は別の状態にする。

```text
検出
→ 候補
→ 採用／見送り
→ 未着手
→ 対応中
→ 実施済み
→ 効果測定中
→ 改善／変化なし／悪化／判定不能
```

画面では、候補を統合・順位付けし、次に推奨する3〜5件程度を中心に提示する案がある。

## 12. 単独施策ではなく施策セットを選ぶ

目標は一つの施策だけで達成するとは限らない。利用可能な時間・予算内で、期待貢献の高い施策セットを選ぶ。

例:

| 候補 | 期待効果 | 作業時間 |
|---|---:|---:|
| title改善 | +1.5CV | 30分 |
| 10位ページのリライト | +4CV | 4時間 |
| 内部リンク追加 | +2CV | 1時間 |
| 新規記事作成 | +5CV | 16時間 |

選定時には次を考慮する。

- 施策間の効果を二重計上しない
- 前提となる施策を先に行う
- 同じページを短期間に何度も変更しない
- 効果測定中の追加変更を制御する
- 短期施策と長期施策を組み合わせる
- 利用可能時間と予算を超えない
- 目標へ必要な合計効果に近づける

初期版では説明可能な貪欲選択等の単純な方法から始め、後に施策間の相乗・重複効果を扱う。

## 13. 目標達成までのフェーズ

個別施策の間に、目標達成までの段階と施策のまとまりを置く。

```text
大目標
└─ 戦略・ロードマップ
   └─ フェーズ
      └─ 施策パッケージ
         └─ 原子施策
```

### 13.1 フェーズの例

```text
大目標: 自然検索CVを月20件にする

フェーズ1: SEOの基盤を整える
├─ 計測設定
├─ 重大なインデックス問題の解消
└─ サイト構造の整理

フェーズ2: Aキーワード群で評価を獲得する
├─ 検索意図を分類
├─ 類似キーワードをクラスター化
├─ 中心ページを作成
├─ 補助ページを作成
└─ 内部リンクで接続

フェーズ3: Aクラスターを改善する
├─ 表示・順位が出たページをリライト
├─ CTRを改善
├─ 不足トピックを追加
└─ CV導線を改善

フェーズ4: Bキーワード群へ展開する
└─ Aで得た構成・実績を再利用

フェーズ5: 維持・拡大する
├─ 順位低下を監視
├─ 古い情報を更新
└─ 周辺クラスターへ展開
```

### 13.2 集中と順序

AとBが同程度に目標へ貢献しても、両方へ均等投資するより、Aへ集中してクラスターを完成させ、得たデータと制作手順をBへ展開した方がよい場合がある。

- ページ群と内部リンクをまとまりとして作れる
- 中途半端なクラスターを複数作らずに済む
- 検索意図、順位変化、CVRを先に検証できる
- 記事構成や制作工程を再利用できる
- 複合効果を測りやすい

### 13.3 フェーズの開始・完了条件

フェーズ名だけでなく、データで判定可能な状態を持たせる。

```yaml
name: Aキーワードクラスターを構築する

entry_conditions:
  - 重大なインデックス問題がない
  - GSC連携が完了している
  - Aキーワード群が定義されている

target_state:
  - 中心ページが存在する
  - 主要な検索意図をページ群でカバーしている
  - 補助ページから中心ページへ内部リンクがある
  - 対象ページがインデックスされている

exit_conditions:
  - 必要なページが公開済み
  - 対象ページの大半がインデックス済み
  - 対象クエリで表示が発生している
  - 次の評価時点を迎えている
```

### 13.4 固定的な規模目標への注意

「質の高いページを100ページ作る」は中間目標になり得るが、100ページ自体に普遍的な価値はない。

先に定めるべき状態は次である。

- 事業に必要な主要トピックをカバーしている
- ページの検索意図と役割が重複していない
- 中心ページと補助ページが接続されている
- 公開ページがインデックスされている
- 表示やクリックが発生している
- 品質と更新体制を維持できる

必要なページ数は、対象市場とトピック範囲から結果として算出する。

### 13.5 フェーズの判定例

| 現在状態 | 推奨フェーズ |
|---|---|
| クロール・インデックスに重大問題 | 基盤整備 |
| 対象ページが存在しない | コンテンツ構築 |
| ページはあるが圏外 | 検索意図・品質・対象ページの再設計 |
| 10〜20位で表示あり | 順位改善 |
| 上位だがCTRが低い | 検索結果での訴求改善 |
| 流入はあるがCVしない | コンバージョン改善 |
| 順位・CVとも良好 | 維持・周辺展開 |

サイト全体を一つのフェーズに固定するとは限らない。クラスターや目標ごとに異なるフェーズを持つ可能性がある。

## 14. 抜け漏れを減らす方法

最初からすべてのSEO施策を完全に列挙することは現実的ではない。完全性は、対応関係と未対応領域を検査できる仕組みで高める。

### 14.1 目標から下向きに検査する

```text
目標 → KPI → 変化要因 → 状態 → 施策
```

施策へ到達できない変化要因があれば、施策カタログに不足がある。

### 14.2 データから上向きに検査する

```text
データ → 状態 → ギャップ → 施策 → 目標
```

目標、施策、効果測定のいずれにもつながらないデータは、取得優先度が低い可能性がある。

### 14.3 施策から両方向に検査する

すべての施策型について確認する。

- どの状態を変えるか
- どの目標へ貢献するか
- 適用を判断できるデータがあるか
- 予測できるか
- 実施後に測定できるか
- 前提、競合、相乗効果は何か

### 14.4 カバレッジマトリクス

| 目標・要因 | 状態判定 | 対応施策 | 効果予測 | 効果測定 |
|---|---:|---:|---:|---:|
| インデックス | ○ | ○ | ○ | ○ |
| 掲載順位 | ○ | ○ | △ | ○ |
| CTR | ○ | ○ | ○ | ○ |
| CVR | GA4連携後 | ○ | ○ | GA4連携後 |
| 外部評価 | △ | △ | 困難 | △ |
| AI検索露出 | 未対応 | 未対応 | 未対応 | 未対応 |

空欄、`△`、未対応を、仕様上の欠落または対象外として明示する。

### 14.5 SEOの作用点による網羅

施策カタログは少なくとも次の作用点を横断する。

- 発見・クロール
- インデックス
- 検索意図・関連性
- 検索結果での訴求
- 順位
- ページ競合
- 内部リンク・サイト構造
- 外部評価・信頼性
- 表示速度・UX
- 回遊
- コンバージョン
- 維持・監視

目標 × 作用点 × 対象エンティティ × データソース × 施策型のマトリクスで未対応領域を確認する。

## 15. ユーザー向けの情報設計案

内部データモデルと画面の分類は同一でなくてよい。利用者には次の3領域が分かりやすい可能性がある。

1. **現状を把握する**
   - サイト診断
   - 検索パフォーマンス
   - アクセス・成果
   - 将来の競合・AI検索

2. **目標と改善計画を作る**
   - 目標と期限
   - 現在状態との差
   - フェーズと施策パッケージ
   - 予測効果と必要コスト

3. **施策を実行し、成果を確かめる**
   - 次に推奨する施策
   - 実行状態と修正記録
   - 再診断
   - GSC・GA4による効果測定

「問題発見」「機会発見」は画面の最上位分類ではなく、現状把握や改善候補のフィルターとして扱う案が有力である。

## 17. 初期実装の現実的な範囲

初期段階から自由生成AIに施策を全面的に決めさせず、説明可能な有限の施策型とルールを中心にする。

### 17.1 推奨順序

1. Owtellが扱う目標を定義する
2. 目標をKPIと変化要因へ分解する
3. サイト・ページ・クエリの状態モデルを定義する
4. 主要な施策型20〜30件を作る
5. 各施策型の適用・除外条件を定義する
6. 必要なデータとシグナルを定義する
7. 簡易な予測モデルを設定する
8. カバレッジマトリクスで漏れを確認する
9. 実データで施策インスタンス生成を検証する
10. 実績から係数と優先順位を補正する

### 17.2 初期対象として考えられる施策群

- インデックス阻害要因の解消
- リンク切れ、リダイレクト、canonical等の修正
- title・description改善
- 見出し・不足トピック追加
- 内部リンク追加
- 重複・競合ページの統合または役割整理
- 10〜20位ページの改善
- 高表示・低CTRページの改善
- クリック・順位が低下したページの調査・更新
- 対象キーワードに対応するページ作成
- CTA・導線改善

## 18. 判断原則

- データ取得は、施策生成、優先順位、効果測定のいずれかへ接続する
- 目標だけで具体的な施策を断定しない
- 単一指標だけで施策を断定しない
- 理論上の伸び代と実現可能性を分ける
- 一点予測ではなく、範囲、期間、前提、確信度を示す
- 施策候補と実行を決めた施策を分ける
- 原子施策を記録し、ユーザーには扱いやすいまとまりで見せる
- 単独施策だけでなく、依存関係を含む施策セットとフェーズを計画する
- ページ数や記事数を目的化せず、必要な状態から算出する
- 実施後の変化を因果と断定せず、観測された結果として扱う
- 実行記録と予測誤差を、次回の候補生成と予測改善へ利用する
